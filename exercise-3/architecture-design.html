Préstamos de Renta Particular

Diagnóstico del problema (AS-IS) y propuesta de arquitectura (TO-BE)

1. El problema

El cliente solicita un desembolso desde la Zona Segura. La solicitud viaja de forma síncrona a través del backend Node hasta admwr-api, un sistema legado (.NET Forms) dentro de la red privada IS-VCE, detrás del proxy de INARI.

Síntoma observado

  • El proxy de INARI responde 502 Bad Gateway cuando detecta lentitud o timeout.
  • admwr-api sigue procesando en segundo plano y muchas veces termina ejecutando el desembolso con éxito, aunque el cliente ya recibió un error.
  • El cliente, al ver el error, reintenta manualmente → se genera un segundo desembolso para el mismo préstamo.

Causa raíz

El 502 es el síntoma, no la causa. El problema real combina tres cosas:

#CausaEfecto
1 El timeout del proxy no está alineado con la duración real del proceso en admwr El proxy corta la conexión, pero el backend no se entera y sigue ejecutando (fire-and-forget accidental)
2 No existe idempotencia en la solicitud de desembolso No hay forma de reconocer "esta ya es la segunda vez que me piden lo mismo"
3 El cliente usa un error de transporte como señal de negocio Reintenta manualmente sin control de concurrencia → desembolso duplicado

2. La solución

La idea central: el cliente nunca espera a INARI. Se introduce una capa de orquestación asíncrona con idempotencia y control de concurrencia entre la Zona Segura y el sistema legado.

Qué resuelve cada pieza nueva

  • 202 inmediato + polling/estado: rompe el acoplamiento síncrono cliente-INARI.
  • Idempotency-Key: un reintento del cliente no genera una segunda operación real.
  • Lock por póliza: impide que dos mensajes para la misma póliza se procesen en paralelo.
  • Cola con reintentos controlados: solo reintenta si la operación sigue pendiente, nunca a ciegas.
  • Job de reconciliación: detecta operaciones "huérfanas" (admwr ejecutó, pero la confirmación no volvió) sin que el cliente lo note.

3. Cómo se mapea contra los criterios del reto

CriterioCómo lo cubre el diseño
EscalabilidadCola + worker stateless en Cloud Run, escalan independiente del legado
Resiliencia y reintentosReintentos con backoff solo mientras la operación siga pendiente, nunca a ciegas
Control de concurrenciaIdempotency-Key + lock por póliza + estado persistido antes de invocar admwr
SeguridadMismo perímetro ya existente (Zona Segura, red privada IS-VCE) + JWT/mTLS en componentes nuevos
CostoServicios managed de bajo costo (Pub/Sub o Cloud Tasks, Memorystore) sobre infraestructura GCP ya existente
